# Secret injection via host-side sidecars — Implementation Plan

**Goal:** let a sandboxed workload use credentialed services (Jira, Confluence, later Slack/IMAP/GitHub) **without the secret ever entering the container**, by giving each capability a host-side sidecar process that the session reaches through the proxy on a reserved mount name.

**Architecture (one paragraph):** a *plugin* — a directory with a manifest, installed under
`%USERPROFILE%\.saife\plugins\<name>\` — declares a sidecar command, a mount name, the secret names it needs, and a health probe. The supervisor starts the sidecar **outside** the container, in its own job object, with the secrets resolved from the Windows credential store and placed only in that process's environment. Inside the container the workload addresses the capability as plain HTTP to `<mount>.sandbox.invalid`; the session proxy recognises the reserved suffix, authenticates the request with the session token, and relays it to the sidecar on host loopback. The workload holds no credential, the audit records which alias was used and which upstream was touched, and the sidecar — not the worker — decides which upstream operations are allowlisted.

**Tech stack:** Rust (existing crate, bin-only, no new async runtime), `windows` crate for Credential Manager + DPAPI, `mxc-sdk`/proxy as shipped, XAML-free plain-HTTP facade over the existing absolute-form forward path (`src/net/proxy.rs:3033`).

---

## 1. Why this shape, and what was measured first

Facts this design is built on, not assumed:

| fact | evidence |
|---|---|
| The container's **only** reachable endpoint is the session proxy | `--allow-domain` works through it; a listener + `Connect` probe to `127.0.0.1` inside the container is refused (`WSAEACCES`), measured 2026-10-23 |
| Loopback *to the proxy* is fine, loopback *to anything else* is not | same probe; `ingress.host_loopback=allow` exists only for the proxy path (`src/net/mxc.rs:2068`) |
| DPAPI is already available in-tree, user scope | `src/signing.rs:17` (`CryptProtectData`/`CryptUnprotectData`) |
| ADR-0001 deliberately did **not** port omac's sidecar/skills architecture | `docs/adr/0001-omac-derived-network-hardening.md:191` |
| F-2 sketched a simpler variant: proxy header injection, CredMan, `--credential` | `docs/notes/future-ideas.md:184` |
| omac's model: skill manifest → host-side sidecar → facade; secrets in the sidecar's env only | `omac-ref/.opencode/skills/echo-rest/omac.yaml` (`sidecar`, `mount`, `secrets`, `health`), `scripts/sidecar.py` |

The consequence for our platform: omac's Unix-socket bridge cannot be ported literally (a filesystem grant for a socket widens the policy, and AF_UNIX under PSEC is unproven here). The proxy **is** our bridge — it already sits on a loopback port the container is allowed to reach, it already parses absolute-form HTTP (`handle_forward`), and it already knows the session's token. So the facade becomes a proxy route rather than a new transport.

## 2. Decisions to record (D-1 … D-10)

**D-1 — Transport: reserved-host façade through the proxy, not a socket.**
Requests to `http://<mount>.sandbox.invalid[:port]/…` are the only way into a sidecar. `.sandbox.invalid` is never resolved and never dialled; a `CONNECT` to such a name is refused with `facade_requires_http` (so a client cannot try to TLS-pin or tunnel past the facade). Rejected: AF_UNIX bridge (unproven under PSEC, needs a filesystem grant), raw loopback TCP to a second port (measured denied, and would need a policy exception that also re-opens loopback generally).

**D-2 — Two distinct credentials, neither of them the secret.**
- workload → façade: the existing per-run `RunToken` in `Proxy-Authorization` (already required by the listener), plus the mount must be declared for that session.
- façade → sidecar: a separate per-session **facade token** generated by the supervisor, placed in the sidecar's env (`SIDECAR_FACADE_TOKEN`) and compared in constant time. It exists so a hostile local process that guesses the sidecar's port cannot use it as a credential oracle.

**D-3 — The sidecar is a deputy, so it must be narrow.**
The workload is untrusted; anything the sidecar exposes, the workload can call. Therefore sidecars expose **explicit operations** (`GET /jira/issue/:key`, `GET /jira/search?jql=`), never a transparent pass-through proxy, and every request is checked against an allowlist of `(method, path pattern)` before it reaches the upstream. The manifest cannot widen this at runtime. This is the confused-deputy boundary and the plan's central security rule.

**D-4 — Secrets live in Windows Credential Manager, keyed `sandbox/<skill>/<NAME>`.**
Written once by `saife secret set`, read by the supervisor at launch, injected only into the sidecar's environment, zeroised after spawn where the platform allows. The profile and the manifest reference **names**, never values. A `Secret`/`SecretValue` type (like `RunToken`) redacts `Debug`/`Display` and refuses `Serialize`, so a value cannot reach the audit or a `--json` dump by accident.

**D-5 — Fail closed, always.**
A declared skill whose sidecar does not become healthy within its `health.timeout_ms` refuses the session (`sidecar_unhealthy`, exit 5) — there is no "run without the sidecar" fallback for a capability the caller asked for. This mirrors `--allow-domain`'s posture: asking for a capability and silently not getting it is the failure mode this project exists to prevent.

**D-6 — Lifecycle is the supervisor's, and it is bounded.**
Start order: proxy bound → secrets resolved → sidecars spawned (job object, `KILL_ON_JOB_CLOSE`) → health gate → child. Teardown kills the job after the child exits, and `Drop` kills it on every early return. Sidecar stdout/stderr go to `<session>/sidecar-<mount>.log` with the token and every secret value redacted at write time.

**D-7 — Audit gets a sidecar vocabulary, and never a value.**
New leaves: `op=SIDECAR` at spawn/exit (`mount`, `pid`, `health`, `secrets` as **names only**), and one leaf per facade request (`mount`, `path`, `upstream_host`, `status`). `audit show` gains the keys; `KNOWN_KEYS` and the docs taxonomy are updated in the same change. A secret value must be unrepresentable in the leaf type, not merely unprinted.

**D-8 — Plugins live under the user's sandbox home, and are extensible by the operator.**
`%USERPROFILE%\.saife\plugins\<name>\plugin.json` + its `scripts/`, so adding a capability is a
filesystem drop-in that needs no rebuild and no admin (the user's decision, 2026-10-23). Repo samples
mirror the built-in ones under `sandbox/plugins/` for review; the *installed* copy is what runs. A
plugin's directory is its cwd, so `command: ["python", "sidecar.py"]` is self-contained. The manifest fields mirror omac's, minus the macOS/Linux bits: `name`, `mount`, `command`, `secrets[]` (name/required/pattern), `config{}` (typed, non-secret), `health{path,timeout_ms,interval_ms}`, `operations[]` (the D-3 allowlist), `upstream` (fixed base URL per operation set).

**D-9 — The sidecar's own egress is a policy surface, and it is fixed.**
A sidecar runs outside the container and therefore outside the session's network policy. Its upstream is pinned in the manifest (host + optional port) and the sidecar refuses any request whose resolved upstream differs; no `--allow-domain` from the workload can widen it. Recorded so "the sandbox is proxy-only" stays a true statement about the workload, and the deputy's reach is a documented, narrow exception.

**D-10 — Env-var injection stays available but is opt-in and recorded as weaker.**
`--env-credential <NAME>` (F-2) remains for tools that cannot speak HTTP; it puts the value in the child's environment, is refused unless explicitly requested, and writes an audit leaf saying so. Documented as strictly weaker than the façade (the workload can print it).

## 2a. POC scope (the first deliverable, smaller than this plan)

A dummy plugin proves the transport end-to-end before any secret handling exists:

- `~/.saife/plugins/tngtech/` — `plugin.json` + `sidecar.py` (stdlib only). It fetches
  `https://www.tngtech.com/` and serves it at `GET /`; `GET /status` is the health probe; every other
  path and every request without the per-session `X-Facade-Token` is refused.
- Rust: plugin discovery, sidecar spawn (host-side, job-scoped), health gate, façade routing for
  `http://tngtech.sandbox.invalid/`, `CONNECT` to that suffix refused.
- The proof: inside the sandbox `curl.exe http://tngtech.sandbox.invalid/` returns the homepage, while
  `curl.exe https://www.tngtech.com/` in the same session is still denied — the container's egress did
  not widen; only the façade did.

Not in the POC: secrets (P2), non-GET methods, per-operation allowlists enforced by the supervisor,
AppContainer-path plumbing, SSE size limits.

## 3. Threat model (what this must survive)

| threat | control |
|---|---|
| Workload prints/exfiltrates the secret | value never enters the container; only the alias does (D-1, D-4) |
| Workload abuses the deputy to reach anything the credential can | per-operation allowlist, no pass-through (D-3) |
| Another local process talks to the sidecar | facade token, constant-time compare, port bound to loopback only (D-2) |
| Workload tunnels TLS through the façade to bypass inspection | `CONNECT <mount>.sandbox.invalid` refused; facade is plain HTTP only (D-1) |
| Sidecar compromised / crashes mid-session | job object kill, health leaves in audit, session exit code reflects it (D-6) |
| Secret leaks into logs | redacted-at-write, redacting `Debug`, no `Serialize` (D-4, D-7) |
| Sidecar becomes a general egress path | pinned upstream per manifest, refused otherwise (D-9) |
| Stale sidecar reused across sessions | per-session spawn + per-session tokens; no reuse (D-2, D-6) |

## 4. Phases and tasks

Each task is TDD: red first, watch it fail, minimal implementation, green, gates, commit. Gates are the standing ones (bin-only `cargo test --bin saife`, both feature states, clippy 0, CRLF, live legs with a rebuilt `target/debug/saife.exe`).

### P1 — Skill manifest and registry
- **T1.1** `src/skill/manifest.rs`: parse `skill.json` into `SkillManifest` (`name`, `mount`, `command`, `secrets`, `config`, `health`, `operations`, `upstream`). Test: malformed mount (`^[a-z0-9][a-z0-9-]{0,30}$`, reserved names refused), unknown fields refused, missing `schema_version` refused.
- **T1.2** `src/skill/registry.rs`: load from `~/.saife/skills/*/skill.json`, deterministic order, duplicate mount refused, `--skill <name>` on `run` selects a set.
- **T1.3** CLI: `saife skill list|show <name>`; `run --skill a --skill b` (this is where multiple capabilities compose, unlike `--profile`).
- **T1.4** Profile integration: `network.facade.enabled` default **false**; a session with `--skill` implies it.

### P2 — Secret store
- **T2.1** `src/secret/store.rs` over `CredReadW`/`CredWriteW` (generic credentials, target `sandbox/<skill>/<NAME>`), with a trait so tests inject an in-memory store.
- **T2.2** `SecretValue` type: redacting `Debug`/`Display`, no `Serialize`, `Zeroize` on drop; test asserts `format!("{:?}")` and `to_string()` contain no value bytes.
- **T2.3** CLI: `saife secret set|list|delete` (list shows alias + `sha256(prefix)[:8]` fingerprint, never the value), mirroring omac's `/whoami` proof idea.
- **T2.4** Resolution at launch: manifest `secrets[]` → store lookup; missing required secret refuses with `secret_missing: <NAME>` before any process starts.

### P3 — Sidecar supervisor
- **T3.1** `src/skill/sidecar.rs`: spawn (`command`, cwd = skill dir, env = inherited + `SIDECAR_PORT` + `SIDECAR_FACADE_TOKEN` + secret env), job object with `KILL_ON_JOB_CLOSE`, stdout/stderr to the session log with redaction.
- **T3.2** Health gate: poll `health.path` on the sidecar's port until 2xx or timeout; `sidecar_unhealthy` refusal; `SIDECAR` audit leaf on success/failure.
- **T3.3** Teardown: kill on drop and after child exit; live leg asserts the sidecar port is **closed** afterwards by connecting to it (not by inferring from `Drop`).
- **T3.4** Fake sidecar for tests (`src/skill/tests/fixtures/echo-sidecar.rs`, a tiny std-lib HTTP server) so no test needs Python.

### P4 — Façade in the proxy
- **T4.1** Route parsing in `handle_forward`: `<mount>.sandbox.invalid` → facade dispatch; unknown mount → 404 `facade_unknown_mount`; reserved-suffix `CONNECT` → 403 `facade_requires_http`.
- **T4.2** Relay: rewrite to `127.0.0.1:<sidecar_port><path>`, set `SIDECAR_FACADE_TOKEN`, strip hop-by-hop headers and any client-supplied `Authorization`/`Proxy-Authorization` for facade hops, one request per connection, streaming passthrough (SSE must not buffer).
- **T4.3** Audit leaf per facade request; secrets unrepresentable (type-enforced).
- **T4.4** Live legs: echo sidecar round-trip, SSE stream (assert frame-by-frame arrival), oversized header refused, unknown mount 404, token-less request 407.

### P5 — Real skills: Jira and Confluence
- **T5.1** `skills/jira/sidecar` (Rust binary in-crate, `src/bin/sidecar-jira.rs`): operations `GET /jira/issue/:key`, `GET /jira/search?jql=…` (bounded), `POST /jira/comment` behind a per-operation allowlist; Basic auth `email:api_token` from the store; upstream pinned to `<site>.atlassian.net` read from a non-secret config field.
- **T5.2** `skills/confluence/sidecar` with page-read operations.
- **T5.3** Documentation: `docs/USER-GUIDE.md` chapter "Skills and secrets" with a worked example (store a token, run a session, `curl` an issue through the façade, show the audit leaf and the absence of the secret).
- **T5.4** Acceptance: against a **fake** upstream first (deterministic), then a manual checkpoint against the real instance (user-run, one command, expected status).

### P6 — Hardening review and docs sweep
- **T6.1** Independent review: confused deputy, SSRF from sidecar (path traversal into a different upstream host), header smuggling, SSE/keep-alive framing, token comparison, redaction completeness.
- **T6.2** `docs/adr/0005-sidecar-secret-injection.md` recording D-1…D-10 with the rejected alternatives; amend ADR-0001's "does not adopt sidecars" clause to point at it.
- **T6.3** Grep for stale claims: README/AGENTS/USER-GUIDE/DEVELOPERS wording that says secrets are unsupported.

### P7 — Optional, only if asked
- AF_UNIX transport alternative; `1password://`/`apple-password://` resolvers; `--env-credential` mode; per-operation rate limits; secret rotation (`saife secret rotate`).

## 6. Verification

- Unit: manifest validation matrix, secret redaction, facade routing table, relay header rules.
- Live (`#[ignore]`, unelevated): echo sidecar round-trip, SSE frames, sidecar death mid-request, teardown closes the port, unknown mount, token refusal.
- Audit: `saife audit show <sid> --filter 'op=SIDECAR'` and `--filter 'mount=jira'` return the leaves; no leaf contains a secret (a test greps the whole log for the known fixture value).
- Host clean: `tests/Clear-HostTestArtifacts.ps1` must stay `HOST-CLEAN` — sidecars are processes, so the script's stray-process pass gains a `sidecar-*` pattern.
- VM lane: facade scenarios must classify as backend-specific only if the *mechanism* is backend-specific; both backends should pass the echo round-trip.

## 7. Risks and open questions

1. **Deputy scope is the real risk, not transport.** A Jira token is user-scoped: a sidecar that exposes `GET /search?jql=` lets the workload read every issue the token can. The allowlist narrows *shape*, not *reach*. Decide up front whether Jira access is read-only and whether project keys are pinned in config (recommended: pin projects; default deny).
2. **Windows Credential Manager as an API dependency**: `CredRead`/`CredWrite` are stable, but the store is per-user and not portable to the VM lane's second account (parked). Tests must inject a fake store; the VM lane only covers the flow with `env_passthrough`-style fixtures.
3. **Streaming**: SSE and large responses must stream through the relay; the proxy currently concludes a forward after one request. Budget a review round for framing.
4. **AF_UNIX**: Windows supports it, PSEC's treatment is unproven. Deferred (P7), not rejected on principle.
5. **Sidecar distribution**: a Rust sidecar per skill keeps the toolchain in-tree but grows the binary set; a single `sandbox-sidecar` binary with a `--skill` argument may be the better shape (decide in P5.1 before writing two binaries).
6. **Naming**: `<mount>.sandbox.invalid` depends on a reserved TLD decision; `.invalid` is reserved by RFC 2606, so it can never collide with a real host — keep it, and refuse any manifest whose mount is not a single DNS label.

## 8. Out of scope

- Replacing omac's keychain with our store for the macOS/Linux backends (we are Windows-only).
- A general plugin system; skills are manifests + one process, nothing more.
- Secret sharing between users or machines.
- Persisting sidecars across sessions (F-3 ghost sessions would revisit this).
